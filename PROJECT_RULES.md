# Постоянные правила разработки X-Buddha

## Технологии и архитектура

- Разработка ведётся Mobile First на Next.js, TypeScript и Tailwind CSS.
- Используется App Router.
- React Server Components используются по умолчанию; Client Components — только для необходимой интерактивности.
- Интерфейс строится из небольших компонентов с ясной ответственностью.
- Количество зависимостей должно оставаться минимальным.
- Контент, ссылки, URL видео и mock-данные хранятся отдельно от JSX.
- Backend, API, CMS, база данных, авторизация и формы не создаются до отдельной задачи.
- Связь с пользователем происходит только через Telegram, WhatsApp и MAX.

## Качество

- SEO закладывается с первого изменения: один H1, корректная иерархия заголовков, metadata и семантическая разметка.
- Интерактивные элементы должны быть доступны с клавиатуры и иметь понятные accessible names.
- Необходимо учитывать `prefers-reduced-motion`, контраст, focus state и отсутствие горизонтального скролла.
- Изображения выводятся через `next/image` с корректным aspect ratio, `sizes`, lazy loading и без деформации.
- Не подключать тяжёлые библиотеки и постоянные ресурсоёмкие анимации без объективной необходимости.

## Утверждённая структура и изображения

- Нельзя менять утверждённую структуру, порядок секций, маршруты, тексты и CTA без согласования.
- Файлы `*slider*` из `public/seed_photos/` используются только в Hero.
- Файлы `*center*` используются для центрального изображения блока факторов оценки.
- Файлы `*footer*` используются в финальном экране.
- Внешние изображения не используются; отсутствующие группы заменяются нейтральными локальными заглушками.

## Документация

- Применяется Documentation First: до реализации изучаются действующие требования, а согласованные изменения требований, архитектуры или этапов сначала фиксируются в профильном документе.
- Для каждого вида сведений используется один источник истины: `AGENTS.md` задаёт поведение AI, `docs/project-plan.md` — этапы и work items, `docs/TODO.md` — оперативные следующие действия, `CHANGELOG.md` — историю, этот документ — постоянные технические правила.
- Одна и та же информация не дублируется между документами; вместо копирования используется ссылка на профильный источник.

## Git Workflow

- Перед изменениями проверять состояние рабочего дерева и сохранять пользовательские и несвязанные с задачей правки.
- Завершённую задачу оформлять отдельным содержательным commit, включая только относящиеся к ней изменения.
- После успешных обязательных проверок отправлять commit в настроенный remote текущей ветки; если remote или доступ отсутствуют, явно зафиксировать это как блокер отправки.
- Не переписывать опубликованную историю и не выполнять force push без отдельного согласования.
