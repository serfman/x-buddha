# X-Buddha — архитектура frontend

## 1. Назначение

Создать frontend коммерческого сайта X-Buddha. Главная страница остаётся автономной, а блог получает опубликованный контент через изолированный серверный слой Directus.

Прототип должен:

- выглядеть как почти готовый коммерческий сайт;
- демонстрировать утверждённую структуру и дизайн на desktop и mobile;
- использовать реальные локальные изображения проекта;
- быть пригодным для последующего развития без полной пересборки интерфейса;
- оставаться простым по архитектуре и дешёвым в поддержке.

## 2. Технологический стек

Обязательный стек:

- Next.js 15+ с App Router;
- TypeScript в strict-режиме;
- Tailwind CSS;
- React Server Components по умолчанию;
- клиентские компоненты только там, где требуется интерактивность;
- CSS-анимации и нативный React вместо тяжёлых библиотек;
- `next/image` для изображений;
- локальные шрифты или `next/font`.

Не подключать:

- backend;
- Supabase;
- БД;
- API routes;
- авторизацию;
- формы;
- загрузку файлов;
- UI-kit ради нескольких элементов;
- Framer Motion без объективной необходимости.

## 3. Маршруты

```text
/
/blog
/blog/[slug]
/privacy
```

`/privacy` содержит фактическое описание технических данных, consent, Яндекс.Метрики, Directus и переходов во внешние мессенджеры. Публичная оферта не размещается: сайт не заключает сделку через checkout или онлайн-оплату, а конкретные условия взаимодействия согласуются непосредственно с клиентом. Удалённый маршрут `/offer` не перенаправляется и возвращает штатную страницу 404.

## 4. Структура главной страницы

Главная содержит только согласованные секции:

1. Header.
2. Hero с автоматическим слайдером.
3. «Факторы оценки статуэтки».
4. «Как узнать стоимость прямо сейчас?».
5. Видео о методах оценки.
6. Финальный экран с тханками и Гималаями.
7. Footer как часть финального экрана или непосредственно под ним.
8. Плавающая кнопка «Написать» на mobile.

Запрещено добавлять новые смысловые секции: отзывы, кейсы, экспертность, FAQ, цифры, партнёров, сертификаты, категории и другие типовые блоки лендинга.

## 6. Работа с изображениями

Все изображения находятся в `public/seed_photos/`.

Назначение определяется по имени файла:

- `*slider*` — только Hero-слайдер;
- `*center*` — центральное изображение блока факторов оценки;
- `*footer*` — финальный экран.

Правила:

- автоматически получить или вручную составить список файлов по группам;
- не использовать внешние изображения;
- не деформировать изображения;
- использовать `object-fit: cover` только там, где допустимо кадрирование;
- для центральной статуэтки предпочтительно `object-fit: contain`;
- ниже первого экрана включить lazy loading;
- предусмотреть заглушку, если какая-либо группа изображений отсутствует;
- не копировать одно изображение в несколько смысловых ролей без необходимости.

## 7. Данные и конфигурация

Контент, ссылки и параметры вынести из JSX:

```text
src/data/site.ts
src/data/messengers.ts
src/data/evaluation-factors.ts
```

В конфигурации должны храниться:

- тексты секций;
- ссылки Telegram и MAX;
- URL RuTube;
- длительность слайда;
- статьи не хранятся во frontend-конфигурации и поступают из Directus;
- подписи факторов оценки.

## 8. Клиентские компоненты

Клиентскими должны быть только:

- автоматический слайдер;
- mobile-меню;
- bottom sheet мессенджеров;
- при необходимости lazy iframe для RuTube.

Остальные секции — серверные компоненты.

## 9. Слайдер

### Desktop

- одновременно три вертикальных изображения;
- центральное изображение немного крупнее или визуально активнее;
- автоматическое циклическое переключение раз в 6 секунд;
- плавный переход 700–1000 мс;
- без свайпа и drag;
- без обязательных стрелок;
- при смене обновляется вся тройка, а не только центральный кадр;
- корректная работа при 3, 4 и большем количестве изображений.

### Mobile

- одно изображение;
- автоматическая смена по таймеру;
- нативный горизонтальный свайп переключает изображения, не блокируя вертикальную прокрутку;
- небольшие случайные горизонтальные движения не переключают слайд;
- можно оставить минимальные индикаторы текущего кадра.

### Доступность

- пауза при `prefers-reduced-motion`;
- изображения имеют alt;
- таймер очищается при размонтировании;
- переключение не должно вызывать layout shift.

## 10. Блок факторов оценки

Desktop-композиция:

- крупная статуэтка в центре;
- подписи слева и справа;
- SVG-линии и светящиеся точки поверх отдельного слоя;
- координаты точек и линий хранятся в данных, а не захардкожены внутри одного JSX-монолита;
- размерная линия справа;
- декоративная орбита или световое кольцо допустимы, но не должны мешать чтению.

Mobile-композиция:

- статуэтка с маркерами остаётся отдельным sticky-элементом над плотным списком факторов на экранах достаточной высоты;
- нумерованные маркеры на изображении;
- список факторов с соответствующими номерами сохраняет обычный вертикальный поток и не накладывается карточками на статуэтку;
- на экранах малой высоты используется обычная последовательная композиция без sticky;
- без попытки уменьшить desktop-схему целиком;
- без горизонтального скролла.

Общий footer вынесен в переиспользуемый компонент и используется в финальной сцене главной и на `/blog`. Карточка в списке статей является одной семантической ссылкой целиком, без вложенных ссылок.

## 12. SEO

SEO реализуется штатными средствами App Router без сторонних библиотек:

- один H1 на страницу;
- корректная иерархия H2/H3;
- централизованные origin, общие тексты и глобальный OG fallback находятся в `src/lib/seo.ts`;
- canonical origin задаётся серверной переменной `SITE_URL`, которая обязательна перед production; локальный fallback `http://localhost:3000` нужен только для разработки и проверочного build;
- metadata и canonical настроены для `/`, `/blog` и опубликованных `/blog/[slug]`;
- глобальный Open Graph fallback и SEO/OG-поля статей из Directus;
- семантические `header`, `main`, `section`, `article`, `footer`;
- человекочитаемые slug;
- опубликованные CMS-статьи индексируемой структуры;
- `src/app/sitemap.ts` получает только опубликованные статьи и при недоступном Directus возвращает статические публичные маршруты;
- `src/app/robots.ts` разрешает публичные страницы, закрывает служебные и preview-маршруты и указывает sitemap;
- заполненная `/privacy` индексируется;
- юридические страницы не добавляются в sitemap автоматически: необходимость оценивается отдельно после согласования документов;
- главная выводит `Organization` и `WebSite`, статья — `BlogPosting` с фактическими CMS-данными.

Для статьи действуют fallback-цепочки `seo_title → title`, `seo_description → excerpt`, `og_image → cover → /og.png`. Отсутствующая, draft- или недоступная статья получает `noindex`; публичный data layer по-прежнему запрашивает только `status = published`.

## 13. Производительность

Целевые ограничения:

- без тяжёлого фонового видео;
- без canvas/WebGL;
- без постоянной анимации большого количества частиц;
- декоративные звёзды — CSS/background image;
- минимальный JavaScript;
- никакой гидрации всей страницы;
- изображения ниже первого экрана lazy;
- iframe RuTube загружать после клика или при приближении к viewport.

## 14. Критерии готовности архитектуры

- проект запускается командами `npm install` и `npm run dev`;
- `npm run build` проходит без ошибок;
- TypeScript не содержит `any` без необходимости;
- UI не зависит от административных credentials Directus;
- нет горизонтального скролла на 360 px;
- структура не усложнена раньше времени;
- дизайн сохраняется при обновлении контента через CMS.

## 15. Блог и Directus

Directus выбран как headless CMS, потому что предоставляет готовые коллекции, rich-text редактор, медиатеку, статусы публикации и granular permissions без разработки собственного административного интерфейса.

```text
Directus
  ↓
server-side data layer (`src/lib/directus/`)
  ↓
Next.js Server Components + revalidation
  ↓
существующий Blog UI
```

Публичный frontend обращается к Directus без токена. Public policy разрешает только чтение записей `articles` со `status = published` и изображений. UI-компоненты не выполняют CMS-запросы напрямую.

Коллекция `articles` содержит `id`, `status`, `title`, уникальный `slug`, `excerpt`, HTML rich content в `content`, `cover`, `published_at`, автоматически обновляемый `updated_at`, `seo_title`, `seo_description` и `og_image`. HTML очищается allow-list санитайзером на сервере; изображения rich content принимаются только с `/assets/` настроенного Directus origin.

Список и страницы статей кэшируются серверным `fetch` Next.js с revalidation раз в 5 минут. Ошибка CMS изолируется маршрутами блога; mock-контент не используется как production fallback. Динамическое обновление требует серверного Next.js runtime, поэтому статический `output: export` не применяется.

Развёртывание схемы и редакторский процесс описаны только в [инструкции Directus](../cms/directus.md).

## 16. Аналитика и конверсионные события

`src/components/analytics/AnalyticsConsent.tsx` до загрузки аналитики запрашивает явный выбор «Принять» или «Отклонить» и сохраняет его локально вместе с версией consent. При изменении версии выбор запрашивается повторно. Отказ не влияет на страницы, блог, изображения, навигацию или внешние ссылки.

Яндекс.Метрика подключается в `src/components/analytics/YandexMetrika.tsx` только при сохранённом согласии и наличии числового `NEXT_PUBLIC_YANDEX_METRIKA_ID`. Для App Router счётчик инициализируется один раз с `defer: true`, а последующие просмотры маршрутов отправляются методом `hit`; начальный `hit` повторно не посылается. Без согласия или ID внешний скрипт, pixel fallback и вызовы API отсутствуют.

Все CTA используют единый `src/lib/analytics.ts` и цели:

- `messenger_telegram_click`;
- `messenger_max_click`.

В параметре `location` передаётся одно из значений: `hero`, `how_to`, `final`, `mobile_sheet`, `blog`. Production использует счётчик `111463994`. Для отчётов по конверсиям в интерфейсе этого счётчика вручную создаются две цели типа «Целевое событие» с условием «совпадает» и идентификаторами `messenger_telegram_click` и `messenger_max_click`; frontend уже отправляет их через `reachGoal`. Код счётчика и события проверяются на production после каждого изменения consent-механики или CTA.

Формы, загрузка фотографий и пользовательская авторизация отсутствуют. Фотографии и сообщения передаются напрямую во внешние Telegram/MAX, а контакт по юридическим вопросам указан как `@Lanumax`; персональные реквизиты владельца в юридических страницах не публикуются.

Предзаполненный текст в текущие адресные ссылки не добавляется: Telegram-контакт задан ссылкой по номеру телефона, а MAX — ссылкой на профиль. Официальные share-ссылки обоих сервисов открывают выбор получателя, а не гарантированный диалог с указанным контактом; Telegram Business-ссылка клиентом не предоставлена. Поэтому обычные проверенные адресные ссылки сохраняются.

## 17. Production runtime

Production-версия работает на одном VPS в трёх контейнерах: standalone Next.js, Directus и PostgreSQL. Nginx на хосте завершает TLS и проксирует публичные домены к loopback-портам frontend и CMS; PostgreSQL доступен только во внутренней Docker network.

Для Directus разделены адреса по назначению: `DIRECTUS_URL=https://admin.xbuddha.org` формирует публичные URL файлов и image allow-list, а `DIRECTUS_INTERNAL_URL=http://directus:8055` используется только серверным data layer. При отсутствии внутренней переменной data layer сохраняет совместимый fallback на `DIRECTUS_URL`.

Полная схема инфраструктуры, env, SSL, backup, deployment и rollback поддерживается только в корневом [DEPLOY.md](../../DEPLOY.md).
