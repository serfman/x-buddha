# Задача 004. Система объективного прогресса проекта X-Buddha

## Цель

Внедрить постоянный механизм отображения прогресса X-Buddha по крупным этапам проекта.

После выполнения каждой задачи итоговый ответ AI/Codex должен автоматически завершаться актуальным блоком:

ПРОГРЕСС X-BUDDHA

P0 ██████████ 100%

P1 ██████████ 100%

P2 ██░░░░░░░░ 23%

...

Проценты запрещено определять субъективно.

Прогресс рассчитывается исключительно по фактически выполненным work items соответствующего этапа.

---

# 1. Источник истины

Основным источником прогресса сделать:

`docs/project-plan.md`

Не создавать отдельный файл со вторым независимым набором процентов.

В `docs/project-plan.md` каждый этап должен содержать:

- ID этапа;

- понятное название;

- конечный результат этапа;

- чек-лист атомарных work items.

Каждый work item имеет только два состояния:

- `[ ]` — не выполнен;

- `[x]` — выполнен.

Проценты вручную в документации не хранить.

# 3. Формула прогресса

Для каждого этапа:

`progress = completed_work_items / total_work_items * 100`

Правила:

1. Учитываются только work items текущей версии `docs/project-plan.md`.

2. Каждый пункт имеет одинаковый вес.

3. Частично выполненный пункт остаётся `[ ]`.

4. Процент округляется до ближайшего целого числа.

5. Запрещено вручную назначать процент по субъективной оценке.

6. Если добавился новый обязательный work item, знаменатель изменяется и процент может уменьшиться — это корректное поведение.

7. Этап получает 100% только когда все его work items имеют `[x]`.

# 4. Progress bar

Использовать шкалу из 10 символов.

Формат:

`██████████`

Количество заполненных сегментов:

`floor(progress / 10)`

Исключение:

при `progress = 100` показывать 10 заполненных сегментов.

Остальные сегменты:

`░`

Примеры:

- 0% → `░░░░░░░░░░`

- 23% → `██░░░░░░░░`

- 50% → `█████░░░░░`

- 99% → `█████████░`

- 100% → `██████████`

# 6. Обновление состояния

После выполнения любой следующей задачи:

1. Определить, какие work items реально завершены.

2. Обновить соответствующие `[ ]` → `[x]` в `docs/project-plan.md`.

3. Не отмечать связанные пункты автоматически, если задача их фактически не выполнила.

4. Обновить `TODO` и `CHANGELOG` согласно правилам проекта.

5. Рассчитать progress каждого P-этапа.

6. Вывести блок прогресса последним блоком ответа.

---

# 7. Постоянное правило для AI

Закрепить механизм в `AGENTS.md`.

Добавить правило:

- после каждой завершённой задачи читать актуальные work items из `docs/project-plan.md`;

- рассчитывать проценты математически;

- выводить блок `ПРОГРЕСС X-BUDDHA` последним блоком ответа;

- не использовать субъективные проценты;

- при изменении состава этапов сначала обновлять `docs/project-plan.md`;

- `docs/project-plan.md` является единственным источником истины для структуры этапов и расчёта прогресса.

Не дублировать полный список work items в `AGENTS.md`.

В `AGENTS.md` должна находиться только инструкция по механизму и ссылка на источник истины.

---

# 8. Правила документации

Если в проекте уже существует постоянный документ с правилами ведения документации — использовать его.

Если ранее согласованные правила Git Workflow / Documentation First / Single Source of Truth ещё не закреплены в постоянной документации, добавить их в рамках этой задачи в подходящий документ, не создавая отдельную задачу.

Принцип:

- `AGENTS.md` — поведение AI;

- `docs/project-plan.md` — этапы, work items и источник прогресса;

- `TODO` — оперативные следующие действия;

- `CHANGELOG` — история;

- `PROJECT_RULES.md` — технические правила.

Не дублировать одну и ту же информацию между файлами.

---

# 9. Проверка существующего статуса

Перед фиксацией начальных процентов проверить фактическое состояние проекта и историю выполненных задач.

Не ориентироваться только на старый `TODO`, если он уже не соответствует факту.

Известно, что задача 003 завершена: frontend перенесён, H1 и типографика доработаны, lint/build прошли.

Проверить остальные пункты P0/P1 по проекту и выставить `[x]` только на основании факта.

---

# Не входит в задачу

- разработка новых пользовательских функций;

- CMS;

- интеграция мессенджеров;

- SEO-доработки;

- production deployment;

- изменение дизайна.

Эта задача меняет только механизм проектного управления и документацию.

---

# Definition of Done

- в `docs/project-plan.md` присутствуют P0–P7 с атомарными чек-листами;

- начальные статусы синхронизированы с фактическим состоянием проекта;

- формула расчёта однозначна;

- `AGENTS.md` содержит постоянное правило вывода прогресса;

- отсутствует отдельный вручную поддерживаемый процент;

- после выполнения задачи итоговый ответ уже содержит рассчитанный блок `ПРОГРЕСС X-BUDDHA`;

- TODO/CHANGELOG обновлены;

- выполнены commit и push согласно постоянным правилам проекта, если Git Workflow уже закреплён или добавлен этой задачей.
