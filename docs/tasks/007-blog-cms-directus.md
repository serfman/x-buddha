# Задача 007. Подключение CMS Directus для блога

## Цель

Перевести существующий frontend-блог X-Buddha с mock-данных на управляемый контент через Directus.

После выполнения:

- статьи создаются и редактируются через Directus;
- `/blog` получает опубликованные статьи из CMS;
- `/blog/[slug]` отображает конкретную статью;
- поддерживаются изображения и форматированный текст;
- предусмотрены SEO-поля;
- draft-статьи не отображаются на публичном сайте.

Не менять утверждённый дизайн сайта без необходимости.

---

# 1. Сначала проверить текущую архитектуру

Изучить:

- существующие `/blog` и `/blog/[slug]`;
- текущие mock-данные;
- `docs/architecture/*`;
- `PROJECT_RULES.md`;
- `AGENTS.md`;
- `docs/project-plan.md`.

Не создавать параллельную архитектуру блога, если текущие компоненты можно переиспользовать.

---

# 2. CMS

Использовать Directus.

Подключение должно быть изолировано от UI.

Не выполнять запросы Directus непосредственно внутри презентационных компонентов.

Создать отдельный data-access слой, например:

```text
lib/
  directus/
    client.ts
    articles.ts
```

или использовать существующую подходящую структуру проекта.

---

# **3. Модель статьи**

Создать коллекцию `articles`.

Минимальные поля:

- `id`;
- `status`;
- `title`;
- `slug`;
- `excerpt`;
- `content`;
- `cover`;
- `published_at`;
- `updated_at`;
- `seo_title`;
- `seo_description`;
- `og_image`.

## **Status**

Минимально:

- draft;
- published.

На публичном сайте выводить только `published`.

## **Slug**

- обязательный;
- уникальный;
- человекочитаемый;
- используется в `/blog/[slug]`.

---

# **4. Контент статьи**

Статья должна поддерживать не только plain text.

Необходимо обеспечить возможность использовать:

- абзацы;
- H2;
- H3;
- списки;
- выделение текста;
- ссылки;
- изображения;
- цитаты.

Выбрать наиболее простой поддерживаемый Directus способ хранения rich content без разработки собственного редактора.

Не усложнять решение без необходимости.

---



# **5.**

`/blog`

Заменить mock-источник данных на Directus.

Выводить:

- обложку;
- заголовок;
- excerpt;
- дату;
- ссылку на статью.

Сортировка:

от новых публикаций к старым.

Не выводить draft.

Сохранить существующий дизайн карточек.

---



# **6.**

`/blog/[slug]`

Получать статью по `slug`.

Отображать:

- заголовок;
- дату;
- cover;
- основной rich content;
- CTA оценки;
- Telegram;
- MAX.

Сохранить существующую визуальную систему.

Если статья не существует или не опубликована — использовать корректный 404.

---

# **7. SEO статей**

Использовать:

- `seo_title`, если заполнен;
- иначе `title`.

Использовать:

- `seo_description`, если заполнен;
- иначе `excerpt`.

Подготовить metadata для страницы статьи.

OG image:

- использовать `og_image`, если есть;
- иначе `cover`;
- иначе текущий глобальный fallback проекта.

---

# **8. Изображения Directus**

Не использовать неоптимизированные `<img>` без необходимости.

Настроить безопасную работу изображений Directus с Next.js.

Проверить:

- размеры;
- responsive;
- lazy loading;
- отсутствие layout shift.

Не ломать текущую оптимизацию локальных изображений сайта.

---

# **9. Конфигурация**

Все параметры Directus хранить через environment variables.

Например:

```env
DIRECTUS_URL=
```

Секреты не хранить в Git.

Добавить необходимые значения в `.env.example` без реальных секретов.

---

# **10. Поведение при недоступной CMS**

Frontend не должен падать целиком при проблеме Directus.

Для списка статей предусмотреть контролируемое поведение ошибки.

Не возвращаться автоматически к mock-статьям в production.

Mock-данные после успешного подключения удалить или оставить только там, где они нужны для тестирования.

---

# **11. Кэширование**

Использовать возможности Next.js для серверного получения данных.

Не делать блог полностью client-side без причины.

Для опубликованных статей предусмотреть разумное кэширование / revalidation.

Выбрать простой вариант, позволяющий новым публикациям появляться без ручного rebuild всего приложения.

---

# **12. Безопасность**

Публичному frontend не давать административные credentials Directus.

Для чтения опубликованных статей использовать минимально необходимые права.

Draft-контент не должен быть доступен через публичный frontend.

---

# **13. Документация**

Обновить архитектурную документацию.

Зафиксировать:

- почему выбран Directus;
- модель `articles`;
- data flow:

```text

  ↓

Next.js
```

- как добавить изображения.

Не дублировать это между несколькими документами.
