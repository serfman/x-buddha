# Задача 009. Техническое SEO и аналитика

## Цель

Подготовить X-Buddha к индексации поисковыми системами и измерению основных конверсионных действий.

В рамках задачи:

- настроить техническое SEO;

- финализировать metadata;

- настроить Open Graph;

- добавить sitemap и robots;

- добавить необходимую структурированную разметку;

- подключить Яндекс.Метрику;

- настроить события для основных CTA;

- проверить SEO главной страницы и блога.

Юридические документы в рамках задачи не создавать.

---

# 1. Аудит существующей реализации

Перед изменениями проверить текущие:

- metadata;

- Open Graph;

- `robots`;

- `sitemap`;

- canonical;

- favicon/icons;

- SEO-реализацию `/blog`;

- SEO-реализацию `/blog/[slug]`;

- SEO-поля Directus;

- существующий `public/og.png`.

Не создавать дублирующую SEO-инфраструктуру, если часть уже реализована.

Существующие корректные решения переиспользовать.

---

# 2. Главная страница

Настроить финальные SEO metadata для `/`.

Использовать фактическое содержание сайта и терминологию из `client_tz.md`.

Основная семантика:

- оценка буддийских статуэток;

- атрибуция буддийских статуэток;

- оценка буддийских артефактов;

- экспертиза буддийских предметов;

- выкуп буддийских статуэток и артефактов.

Не использовать keyword stuffing.

## Title

Подготовить короткий коммерческий title с главным поисковым интентом.

Ориентир:

`Оценка и атрибуция буддийских статуэток — X-Buddha`

Если после анализа контента существует более точная формулировка — использовать её.

## Description

Подготовить естественное описание страницы примерно 140–160 символов.

Отразить:

- оценку;

- атрибуцию;

- буддийские статуэтки и артефакты;

- онлайн-формат.

Не придумывать преимущества или гарантии, которых нет в `client_tz.md`.

---

# 3. Canonical

Настроить canonical URLs.

Не хардкодить production-домен в разных компонентах.

Использовать одну централизованную настройку, например:

`NEXT_PUBLIC_SITE_URL`

или существующий эквивалент.

Добавить переменную в `.env.example`.

Если production-домен пока не известен:

- не придумывать его;

- обеспечить корректную конфигурацию;

- добавить его получение в TODO перед production.

---

# 4. Open Graph

Проверить существующий:

`public/og.png`

Если он соответствует текущему бренду и содержанию сайта — использовать его.

Не генерировать новое изображение без необходимости.

Настроить:

- `og:title`;

- `og:description`;

- `og:image`;

- `og:url`;

- `og:type`;

- Twitter/X card metadata, если поддерживается существующей архитектурой без отдельной сложности.

Для статей использовать существующий fallback:

1. `og_image`;

2. `cover`;

3. глобальный X-Buddha OG.

---

# 5. Sitemap

Реализовать sitemap средствами Next.js.

В sitemap должны попадать:

- `/`;

- `/blog`;

- опубликованные `/blog/[slug]`;

- публичные юридические страницы после их появления.

Draft-статьи не включать.

Если Directus временно недоступен, генерация sitemap не должна ломать весь production build.

---

# 6. Robots

Настроить `robots.txt` средствами Next.js.

Для production разрешить индексацию публичных страниц.

Не индексировать:

- технические маршруты;

- API/служебные endpoints, если они есть;

- preview/draft-контент;

- другие непубличные страницы.

Добавить ссылку на sitemap.

Не блокировать необходимые CSS, JS и изображения.

---

# 7. Structured Data

Добавить JSON-LD только там, где тип разметки соответствует реальному содержанию.

## Главная

Использовать подходящую комбинацию:

- `Organization` или более точный допустимый тип;

- `WebSite`.

Не придумывать:

- рейтинг;

- отзывы;

- цены;

- адрес;

- телефон;

- юридическое название;

- другие отсутствующие данные.

Использовать только реально известные данные X-Buddha.

## Статья

Для `/blog/[slug]` добавить `Article` или `BlogPosting`.

Использовать реальные данные статьи:

- headline;

- description;

- image;

- datePublished;

- dateModified;

- URL.

Если обязательных данных для свойства нет — не выдумывать их.

---

# 8. Семантическая структура

Проверить:

- один H1 на страницу;

- логичную последовательность H2/H3;

- semantic HTML;

- корректные `<main>`, `<nav>`, `<footer>` там, где применимо;

- alt-тексты;

- descriptive links.

Не менять визуальный дизайн ради SEO.

---

# 9. SEO блога

Проверить `/blog`.

Настроить:

- title;

- description;

- canonical;

- Open Graph.

Для `/blog/[slug]` использовать SEO-поля Directus:

- `seo_title`;

- `seo_description`;

- `og_image`.

Fallback:

`seo_title → title`

`seo_description → excerpt`

`og_image → cover → global OG`

Draft не должен индексироваться или становиться доступным как публичная статья.

---

# 10. Яндекс.Метрика

Подключить Яндекс.Метрику архитектурно корректным способом для Next.js.

ID счётчика хранить в environment variable:

`NEXT_PUBLIC_YANDEX_METRIKA_ID`

Добавить переменную в `.env.example`.

Если ID счётчика пока не предоставлен:

- не придумывать его;

- реализация должна безопасно не загружать Метрику;

- добавить получение ID в TODO.

Не ломать SSR/SSG.

Не ухудшать первоначальную загрузку страницы без необходимости.

---

# 11. События конверсии

Создать централизованный механизм отправки аналитических событий.

Не вызывать Метрику напрямую из каждого UI-компонента.

Минимальные события:

- клик Telegram;

- клик MAX.

Рекомендуемые названия:

`messenger_telegram_click`

`messenger_max_click`

Использовать одинаковые события независимо от места CTA.

При необходимости передавать дополнительный параметр:

`location`

Например:

- `hero`;

- `how_to`;

- `final`;

- `mobile_sheet`;

- `blog`.

Это позволит понимать, какой CTA реально приводит пользователя в мессенджер.

Если Метрика не загружена, клики должны продолжать работать без ошибок.

---

# 12. Подготовленный текст обращения

Проверить возможность передачи предзаполненного сообщения через Telegram и MAX с используемыми типами ссылок.

Не применять нестандартные или ненадёжные URL-схемы только ради закрытия work item.

Если официальный механизм позволяет корректно передать текст — использовать короткое нейтральное сообщение на основе текущего сценария оценки.

Например по смыслу:

`Здравствуйте! Хочу оценить буддийский предмет.`

Не добавлять персональные данные пользователя.

Если для конкретного мессенджера это невозможно или ненадёжно:

- оставить обычную рабочую ссылку;

- зафиксировать техническое ограничение;

- не считать соответствующий work item выполненным искусственно.

---

# 13. Производительность

SEO и аналитика не должны существенно ухудшать Core Web Vitals.

Метрику подключать неблокирующим способом.

Не добавлять тяжёлые сторонние SEO-библиотеки, если возможности Next.js решают задачу штатно.

---

# 14. Юридическая граница задачи

Не создавать:

- политику обработки персональных данных;

- политику конфиденциальности;

- публичную оферту;

- пользовательское соглашение;

- cookie policy.

Данные для юридической части будут получены от клиента позже.

При этом зафиксировать в TODO, что перед production необходимо отдельно проверить влияние Яндекс.Метрики/cookies на требования по персональным данным и пользовательским уведомлениям.

Не утверждать в интерфейсе, что сайт «не собирает персональные данные».
