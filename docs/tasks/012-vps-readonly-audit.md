## Цель

Получить фактическую картину существующего VPS перед размещением X-Buddha и определить безопасную схему совместного размещения X-Buddha с уже работающими сервисами.

На этом этапе сервер НЕ изменять.

## Ограничение: строго read-only

На VPS запрещено:

- создавать, изменять или удалять файлы;

- устанавливать или обновлять пакеты;

- изменять конфигурацию;

- запускать deployment;

- запускать новые контейнеры;

- останавливать или перезапускать существующие контейнеры;

- выполнять `docker compose up/down/restart`;

- изменять Docker networks или volumes;

- изменять Nginx;

- выполнять reload/restart Nginx;

- изменять firewall;

- изменять пользователей, SSH и права доступа;

- изменять cron/systemd;

- изменять DNS;

- выполнять любые другие операции, меняющие состояние VPS.

Если для получения какой-либо информации требуется изменение сервера — пропустить эту проверку и указать это в отчёте.

## Аудит

### 1. Сервер

Определить:

- ОС и версию;

- архитектуру;

- CPU;

- RAM и swap;

- загрузку RAM;

- диски и свободное пространство;

- uptime;

- общую текущую нагрузку.

### 2. Сетевые сервисы

Определить:

- открытые/listening TCP-порты;

- какие процессы занимают порты;

- использование 80 и 443;

- использование других потенциально конфликтующих портов.

Не раскрывать секреты, пароли, токены и содержимое production env.

### 3. Docker

Проверить:

- установлен ли Docker;

- версию Docker;

- наличие Docker Compose;

- запущенные контейнеры;

- опубликованные наружу порты;

- Docker networks;

- Docker volumes;

- restart policies;

- health status контейнеров.

Определить потенциальные конфликты с:

- Next.js;

- Directus;

- PostgreSQL;

- production Compose X-Buddha.

### 4. Reverse proxy

Определить:

- используется ли Nginx;

- какие virtual hosts/server blocks активны;

- какие домены обслуживаются;

- куда проксируются запросы;

- как организован SSL;

- используется ли Certbot;

- как выполняется обновление сертификатов.

Не выводить приватные ключи SSL.

Если используется другой reverse proxy, зафиксировать его вместо Nginx.

### 5. Существующие проекты

Определить:

- какие production-приложения реально находятся на VPS;

- где они расположены;

- какие контейнеры/процессы к ним относятся;

- какие порты, networks и volumes они используют;

- какие сервисы критично не затронуть.

Отдельно проверить, находится ли LikeGallery непосредственно на этом VPS. Не предполагать это только из предоставленного ранее README.

### 6. Firewall и безопасность

Проверить без изменений:

- используется ли UFW/firewalld/другой firewall;

- какие правила действуют;

- доступен ли SSH извне;

- какие публичные порты открыты.

### 7. Совместимость X-Buddha

Сопоставить фактическую конфигурацию VPS с:

- `docker-compose.production.yml`;

- `Dockerfile`;

- `nginx/x-buddha.conf`;

- `DEPLOY.md`.

Определить:

- конфликты портов;

- конфликты имён контейнеров;

- конфликты Docker networks;

- конфликты volumes;

- конфликты Nginx;

- достаточность ресурсов VPS;

- необходимые изменения production-конфигурации X-Buddha.

Ничего из найденного пока не исправлять.

## Документация

Поскольку задача является только аудитом, не изменять production-конфигурацию.

Результаты аудита зафиксировать в документации проекта только если это допускается действующими правилами проекта. Не помещать в Git секреты, credentials, приватные SSH-ключи, содержимое `.env` или другие чувствительные данные.

Обновить прогресс проекта только в соответствии с существующими правилами расчёта фактически выполненных work items.

## Критерии готовности

Задача считается выполненной, если:

- SSH-доступ по подготовленному ключу работает;

- VPS полностью проанализирован в read-only режиме;

- существующие production-сервисы не изменены;

- определены реальные конфликты с X-Buddha;

- оценена достаточность ресурсов;

- предложена безопасная схема размещения;

- сформирован список действий для следующей deployment-задачи.
