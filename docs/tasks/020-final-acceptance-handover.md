# 020 — Final acceptance & handover

## Цель

Провести финальную техническую приёмку X-Buddha, подготовить проект к передаче клиенту и завершить этап разработки.

После выполнения задачи:

- production должен быть проверен;

- инфраструктура должна быть зафиксирована в документации;

- CMS должна быть готова к работе клиента;

- backup/restore и SSL должны быть проверены;

- документация должна соответствовать фактическому состоянию проекта;

- TODO должен содержать только реальные задачи режима поддержки;

- должна быть подготовлена простая инструкция для владельца сайта;

- P7 должен рассчитываться по фактически закрытым work items.

Это приёмочная задача.

Не выполнять дополнительные улучшения дизайна, архитектуры, SEO, производительности или функциональности, если в процессе проверки не обнаружена реальная проблема.

## Включить

### Вход в админку

Адрес:

`https://admin.xbuddha.org`

Не записывать пароль в Git.

Указать, что пароль администратора должен храниться отдельно и безопасно.

### Создание статьи

Пошагово описать:

1. вход в Directus;

2. открытие коллекции статей;

3. создание статьи;

4. заполнение заголовка;

5. slug;

6. Excerpt;

7. основного текста;

8. обложки;

9. SEO Title;

10. SEO Description;

11. сохранение draft;

12. preview/проверку, если существующая архитектура это позволяет;

13. публикацию.

### Excerpt

Объяснить:

Excerpt — короткое описание статьи для карточки статьи и других мест интерфейса, где используется краткое представление материала.

Дать ориентир по длине, соответствующий фактической реализации проекта.

Не утверждать, что excerpt используется поисковиками как meta description, если это не соответствует реализации.

### SEO Title

Объяснить назначение простым языком.

Дать практическую рекомендацию:

- описывает содержание страницы;

- содержит основной поисковый смысл;

- не является набором ключевых слов;

- желательно уникален для каждой статьи.

### SEO Description

Объяснить:

- это краткое описание страницы для поисковых систем;

- должно объяснять содержание статьи и мотивировать открыть её;

- должно быть уникальным.

Дать разумный ориентир по длине, но не представлять его как жёсткое техническое ограничение поисковых систем.

### Изображения

Объяснить:

- какое изображение использовать как cover;

- предпочтительный формат/размер, исходя из фактической реализации;

- не загружать неоправданно тяжёлые файлы;

- использовать содержательные изображения.

### Редактирование

Объяснить:

- как изменить опубликованную статью;

- как временно снять её с публикации;

- последствия изменения slug у уже опубликованной статьи.

Особо предупредить:

не менять slug опубликованной статьи без необходимости, поскольку старый URL может перестать работать, если redirect не реализован.

# 4. Проверка production infrastructure

Провести read-only проверку текущего состояния VPS.

Проверить:

- Docker containers;

- health status;

- restart count;

- Nginx;

- свободное место;

- RAM;

- swap;

- Docker disk usage;

- основные application logs;

- Nginx errors.

Не выполнять очистку Docker, удаление volumes или другие потенциально destructive действия без реальной необходимости.

---

# 5. Public ports

Проверить фактическую публичную доступность портов.

Ожидаемо доступны:

- 22;

- 80;

- 443.

Не должны быть публично доступны:

- Next.js internal port;

- Directus internal port;

- PostgreSQL.

Если конфигурация отличается — сначала определить причину.

---

# 6. SSL

Проверить:

- `xbuddha.org`;

- `www.xbuddha.org`, если он используется существующей production-конфигурацией;

- `admin.xbuddha.org`.

Проверить:

- валидность сертификатов;

- срок действия;

- HTTPS redirect;

- Certbot renewal configuration.

Проверить renewal безопасным способом, если это предусмотрено текущим [DEPLOY.md](http://DEPLOY.md).

Не перевыпускать рабочие сертификаты без необходимости.

# 8. Backup

Проверить существующую backup-процедуру.

- PostgreSQL;

- Directus uploads.

Проверить:

- файл не пустой;

- понятно, где он хранится;

- процедура описана в `DEPLOY.md`.

Не считать наличие команды backup достаточной проверкой без проверки результата.

# 9. Restore readiness

Restore уже проверялся в рамках подготовки production.

Проверить документацию и убедиться, что процедура восстановления остаётся актуальной после всех последующих изменений.

Не выполнять destructive restore production database.

Если существует безопасный способ повторной проверки через временную БД и это действительно необходимо для закрытия существующего P7 work item — использовать его.

Иначе опереться на уже документированный успешный restore-test и проверить актуальность инструкции.

# 10. Secrets

Проверить:

- `.env*` не отслеживаются Git;

- production secrets отсутствуют в repository history текущих изменений задачи;

- Directus password не находится в документации;

- PostgreSQL credentials не находятся в документации;

- приватные SSH-ключи отсутствуют в репозитории.

Не выводить secrets в отчёт или финальный ответ.

Если обнаружен реально скомпрометированный production secret — не маскировать проблему только удалением из текущего файла; зафиксировать необходимость rotation.
