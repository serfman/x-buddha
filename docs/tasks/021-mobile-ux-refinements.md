# 1. Hero — исправить CTA «Оценить предмет»

## Проблема

На мобильной версии кнопка «Оценить предмет» визуально отображается как основная CTA, но при нажатии ничего не происходит.

## Требование

Кнопка должна выполнять понятное целевое действие.

Оптимальное поведение: при нажатии плавно прокручивать пользователя к основному CTA-блоку с предложением написать для оценки предмета.

Использовать существующий целевой блок страницы, не создавать дублирующий CTA.

Проверить:

- первый клик;

- повторные клики;

- корректную позицию после scroll;

- отсутствие перекрытия sticky/fixed элементами;

- Safari iOS.

# 2. Hero — Telegram и MAX

## Проблема

На mobile Telegram и MAX отображаются практически только как круглые кнопки `TG` и `M`.

Без подписей назначение элементов недостаточно очевидно.

## Требование

На мобильной версии сделать полноценные messenger-кнопки:

- `Telegram`

- `MAX`

Сохранить существующую стилистику проекта и соответствующие иконки/обозначения.

Кнопки должны быть визуально компактнее основной CTA «Оценить предмет», но их назначение должно считываться сразу.

Сохранить:

- существующие реальные URL;

- открытие соответствующего мессенджера;

- события Яндекс.Метрики;

- accessibility;

- достаточный touch target.

Desktop-реализацию не менять.

# 3. Hero — свайп изображений

## Проблема

Слайдер изображений в hero на мобильном устройстве не реагирует на горизонтальный свайп.

## Требование

Добавить полноценное touch/swipe-управление существующим слайдером.

Пользователь должен иметь возможность:

- свайпнуть влево → следующее изображение;

- свайпнуть вправо → предыдущее изображение.

При этом:

- вертикальный scroll страницы не должен блокироваться;

- случайные небольшие горизонтальные движения не должны переключать слайд;

- существующая автоматическая анимация, если она предусмотрена, не должна конфликтовать со свайпом;

- не добавлять тяжёлую carousel-библиотеку, если текущая реализация позволяет решить задачу нативно.

Desktop-поведение не менять.

# 4. «Факторы оценки статуэтки» — sticky-изображение на mobile

## Проблема

На mobile пользователь сначала видит изображение статуэтки с маркерами, а затем при прокрутке изображения уже нет перед глазами и остаётся только список факторов.

Из-за этого теряется связь:

`маркер на статуэтке → соответствующий фактор`.

## Требование

На мобильной версии сделать изображение статуэтки sticky на время просмотра списка факторов.

Желаемое поведение:

1. пользователь доходит до изображения;

2. изображение фиксируется в видимой области;

3. пункты 01–06 последовательно прокручиваются под ним;

4. после окончания блока sticky-состояние корректно завершается и страница продолжает обычную прокрутку.

Не использовать `position: fixed` на всю страницу.

Предпочтительно реализовать через корректный sticky-контейнер `position: sticky`) внутри секции.

Учесть:

- высоту mobile header;

- небольшие экраны;

- Safari iOS;

- отсутствие перекрытия текста;

- отсутствие горизонтального overflow;

- существующие маркеры и размерную линию.

Сами координаты маркеров и содержание факторов не менять.

Если на экранах с очень малой высотой sticky ухудшает UX, предусмотреть безопасный responsive fallback.

Desktop-блок не менять.

# 5. Карточки статей — кликабельна вся карточка

## Проблема

Сейчас переход к статье выполняется только через ссылку/кнопку «Читать →».

На мобильном это создаёт слишком маленькую и неочевидную область взаимодействия.

## Требование

В списке статей вся визуальная карточка статьи должна вести на соответствующую страницу статьи.

Кликабельная область должна включать:

- Cover;

- дату;

- Title;

- Excerpt;

- область `Читать →`.

При этом сохранить корректную HTML-семантику и accessibility.

Не создавать вложенные `<a>`.

Добавить понятное состояние `focus-visible`.

Desktop-внешний вид карточек не менять. Допустимо расширить кликабельную область и на desktop, если это не изменяет существующий визуал и является общей семантически корректной реализацией карточки.

# 6. Footer на `/blog`

## Проблема

На странице списка статей `/blog` отсутствует footer, из-за чего страница выглядит незавершённой и теряются общие элементы сайта.

## Требование

Добавить на `/blog` тот же актуальный footer, который используется на основном сайте.

Не создавать отдельную копию footer.

Переиспользовать существующий общий компонент.

Footer должен содержать актуальные элементы проекта, включая:

- copyright;

- ссылку на Privacy;

- существующий admin access через шестерёнку, если он предусмотрен общей реализацией footer.

Footer должен корректно работать на mobile и desktop.

Это единственное изменение задачи, которое разрешено применять и к desktop `/blog`, поскольку footer является общим структурным элементом сайта.

Не менять:

- утверждённый desktop-дизайн главной страницы;

- тексты;

- изображения;

- координаты маркеров;

- Directus schema;

- структуру данных статей;

- SEO metadata;

- аналитику, кроме сохранения существующих событий;

- messenger URL;

- privacy/cookie logic;

- production infrastructure.

Не выполнять несвязанный рефакторинг.

# Проверка

Обязательно проверить mobile:

- 360 px;

- 390 px;

- 430 px;

- Safari iOS;

- доступный браузер на Chromium.

Проверить:

### Hero

- «Оценить предмет» работает при каждом нажатии;

- Telegram открывает Telegram;

- MAX открывает MAX;

- названия мессенджеров видны;

- swipe слайдера работает;

- вертикальный scroll не ломается.

### Факторы оценки

- изображение sticky;

- пункты 01–06 можно комфортно прочитать;

- изображение остаётся перед глазами;

- sticky корректно начинается и заканчивается;

- маркеры остаются на своих местах.

### Blog

- вся карточка кликабельна;

- открывается правильный slug;

- footer присутствует;

- footer не ломает layout.

Дополнительно проверить desktop 1024/1440 px и убедиться, что утверждённый внешний вид главной страницы не изменился.

Не должно быть horizontal overflow.

Выполнить предусмотренные проектом lint/build/production проверки.

После успешной проверки:

- обновить документацию согласно правилам проекта;

- commit;

- push в `origin/main`;

- deploy на production;

- выполнить production smoke-check.

В конце вывести актуальный `ПРОГРЕСС X-BUDDHA` согласно правилам проекта.
